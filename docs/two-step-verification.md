# Two-step verification

GangsterClub Online supports an optional, account-level two-step sign-in flow. When enabled, a user must complete both of these checks in order:

1. Enter the time-based one-time password sent through the configured email flow.
2. Enter a time-based one-time password generated by the user's configured authenticator app.

The second step is requested only after the email code has been accepted. Authentication is completed only after both codes have been verified successfully.

## Opt-in behavior

Two-step verification is disabled by default. A signed-in user can enable or disable it from the account settings page.

The setting can only be enabled when the account already has an authenticator app configured. The server validates this requirement; a crafted request cannot enable the preference for an account without an active authenticator.

The preference is persisted on the user record as `require_two_step_verification`. Existing accounts remain opted out when the migration is applied.

## Sign-in flow

For an opted-in account with an enabled authenticator:

1. The application starts the normal email OTP challenge.
2. After a valid email OTP, the pending login is retained and the application requests an authenticator-app OTP.
3. After a valid authenticator OTP, the application completes authentication and clears the pending two-step session state.

A failed code does not complete the login. The implementation also clears the additional two-step session flag during logout and when pending authentication state is reset.

Accounts that have an authenticator configured but have not opted in keep the existing authenticator-first behavior. Accounts without an authenticator continue to use the email OTP flow.

## Why this is not described as true MFA

This feature is intentionally named **two-step verification** rather than true multi-factor authentication.

Both checks are possession-based OTP mechanisms:

- access to the email channel used to receive the email TOTP;
- possession of the authenticator secret used to generate the authenticator-app TOTP.

They are two distinct verification steps and normally rely on different systems or devices, so requiring both improves resistance to compromise of only one channel. However, they do not necessarily represent two independent authentication-factor categories such as:

- something the user knows, such as a password;
- something the user has, such as a hardware token;
- something the user is, such as a biometric characteristic.

For that reason, documentation and interface copy should avoid claiming standards-grade MFA or 2FA guarantees. The accurate description is an opt-in, sequential two-step verification flow using email and authenticator-app one-time passwords.

## Security considerations

- Enabling the feature does not make email a trusted or phishing-resistant factor.
- If email and the authenticator app are accessible from the same compromised device or account ecosystem, the practical independence of the two steps is reduced.
- TOTP codes remain susceptible to real-time phishing and relay attacks.
- Recovery and authenticator replacement flows remain security-critical and should continue to require the protections documented in [Authenticator recovery](authenticator-recovery.md).
- Rate limiting, challenge expiration, session-state cleanup, and audit logging should be retained for both verification steps.

## Database migration

The `AddTwoStepVerificationPreference` migration adds the following user preference:

```sql
require_two_step_verification TINYINT(1) NOT NULL DEFAULT 0
```

Run the normal migration workflow after deploying the code:

```bash
cd public_html
php run.php --migrate
```

## Implementation summary

The feature adds:

- a persisted opt-in preference on the user entity and repository;
- account-settings controls and translated status messages;
- server-side validation requiring an enabled authenticator before opt-in;
- explicit session state for a pending two-step login;
- a sequential email OTP then authenticator OTP transition;
- tests covering the two-step authentication state transition.
